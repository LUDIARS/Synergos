# 設計書テンプレート (spec/plan/) — LUDIARS FORMAT_SPEC §6 準拠

対象: Synergos / Curare それぞれの `spec/plan/redesign-<theme>.md`。
言語: 日本語 (コード識別子・プロトコル名・外部製品名は英語のまま)。
文体: 既存 spec と同じ、断定的で短い文。推測は「推定」と明記。根拠は `file:line` または spec パス。

必須構成 (この順序・見出しを使う):

```
# <題名>  (例: Synergos セキュリティ再設計 — 脆弱性と侵害の歯止め)

- 作成日: 2026-10-15
- 対象: <repo> main @ <commit short sha>
- 関連テーマ: security / transfer-efficiency / ai-game-dev のうち本書の位置づけと、他テーマ設計書への相互参照 (同 repo の spec/plan/redesign-*.md と、相手 repo の同名文書)
- 根拠資料: 本 repo の docs/spec/review と、調査した外部資料 (URL 付き)

## 0. 結論 (先に)
   - 3〜8 行で「何が足りないか」「何を作り直すか」「順序」。
   - 「現状のまま運用した場合の最悪シナリオ」を 1〜2 行。

## 1. 背景・ゴール・非ゴール
   - 背景: 現状の設計 (既存 spec の引用) と、ユーザー要求 (AI開発/ゲーム開発・セキュリティ・転送効率の 3 条件を同時に満たす)。
   - ゴール: 測定可能な到達条件 (例: 除名後 60 秒以内に全転送 URL 失効、1 ノード侵害で他組織の実体に到達不能、500 MB PSD 更新の再転送量 < 10%)。
   - 非ゴール: 本書で扱わない範囲と、その判断者。

## 2. 現状分析 — 足りない要素と再設計すべき点
   - 表: ID | 区分 (脆弱性 / 欠落機構 / 設計ギャップ / 非効率 / 未実装機能) | 現状 (file:line 根拠) | 影響 (AI/ゲーム制作での実害) | 重大度 | 再設計の方向
   - 検証済み findings だけを載せる (refuted は載せない)。推測なら「推定」と書く。
   - 「侵害シナリオ別の封じ込め評価」(security の場合) / 「ワークロード別コストモデル」(transfer の場合) / 「ワークフロー別充足表」(ai-game の場合) を小節として持つ。

## 3. 設計判断と選択肢の比較
   - 主要な判断ごとに: 選択肢 A/B/C… を HARNESS §3.5 の 4 軸 (AI 学習量 / 作業コスト / 解決度 / 主目的との一致度) で表にし、採用案と理由。
   - 既存決定 (例: 2026-08-16 差分管理取り下げ、2026-09-08 Cu/Sy/Cr 境界) を尊重しつつ、変更を提案する場合はその決定者 (neco) の再判断事項として明示。

## 4. 再設計の内容
   - 4.x 機構ごと: 目的 → 仕組み (データモデル / API / プロトコル / 設定 / 運用) → 不変条件 → 失敗時の振る舞い → どの既存コードを変えるか (crate/module/file 単位) → 担保手段 (記憶 / フック / ローカル検証ゲート / ランタイム強制)。
   - 相手 repo との契約変更は「契約 ID」(例: SPEC-SY-xxx / SPEC-CU-xxx 形式) を仮置きして双方の文書で同じ ID を使う。
   - データを新設する場合は RULE_DATA_SCHEMA.md の表 (データ名 | 種類 | 権威ソース | 保存先 | 保護要否 | 保護方法) を含める。
   - ドメイン帰属: 変更が属する spec/domains の name と、新設が必要なら新ドメイン案 (REVIEW_DESIGN §0)。

## 5. 実装ステップ・影響範囲・ロールバック方針
   - フェーズ表: フェーズ | 内容 | 対象 crate/module | 依存 | 検証方法 (テスト種別) | ロールバック。
   - 互換性: 既存ノード/クライアント/DB との共存、移行手順 (migrations は追加のみ、DROP 禁止)。

## 6. 検証計画
   - 受入条件 (Revisor/Augur で検証可能な形)。セキュリティは攻撃シナリオごとの再現テストを列挙。性能は計測対象・母集団・目標値。

## 7. 未決事項と判断者

## 8. 参考資料
   - 外部 URL 一覧 (調査ノートから、設計根拠にしたものだけ)。
```

注意:
- 既存 spec (spec/feature, spec/plan, docs/) と矛盾する提案は「変更提案」と明記し、矛盾する既存記述を引用する。
- 「〜かもしれない」で指摘を立てない。確認できないものは「未確認 (理由)」と書く。
- 個人名・個人メールを書かない (役割名で書く)。秘密情報・テスト用固定値を書かない。
- 相手テーマの設計書と重複する内容は要約 + 相互参照に留める (1 機能 1 正本)。
- 文書の冒頭に YAML frontmatter は不要 (既存 spec/plan と同じ素の Markdown)。
