## 1. Content-defined chunking (CDC), dedup, packing, verification

### 1.1 Chunker families and the parameters real systems ship

### 1.2 Xet: packing (xorbs), shards, dedup tiers, CAS API

The Xet protocol is the most complete public spec of a CDC-based blob store built for AI assets, and it is a direct template for a "chunk map" layer on top of Synergos' whole-file CAS.

* **Chunk hash** = BLAKE3 keyed hash of the chunk with a fixed 32-byte `DATA_KEY`. **Xorb hash** = Merkle root over its chunks where an internal node is `BLAKE3_keyed(INTERNAL_NODE_KEY, "<child_hash_hex> : <size>\n" × children)`. **File hash** = `BLAKE3_keyed(32 zero bytes, merkle_root(file chunks))`. **Term verification hash** = `BLAKE3_keyed(VERIFICATION_KEY, concat(raw chunk hashes in [start,end)))`. All hashes 32 bytes. [Xet hashing spec](https://github.com/huggingface/hub-docs/blob/main/docs/xet/hashing.md)
* **Xorb** (pack): ≤ 64 MiB serialized (server rejects larger), ~1,024 chunks on average, hard cap 8,192 chunks; chunks from multiple files may share a xorb. Per-chunk 8-byte header: `version(1) | compressed_size(3, LE) | compression_type(1) | uncompressed_size(3, LE)`. Compression types: `0` none, `1` LZ4, `2` ByteGrouping4LZ4 (bytes regrouped by position mod 4 then LZ4 – targets float/bf16 tensors); store uncompressed if no gain; client picks per chunk (xet-core uses a KL-divergence predictor over per-byte popcounts, `bg4_prediction.rs`). Chunks addressed as `[start, end)` indices inside a xorb. [Xet xorb spec](https://github.com/huggingface/hub-docs/blob/main/docs/xet/xorb.md)
* **Dedup tiers**: (1) in-session hash table; (2) local shard-metadata cache across sessions; (3) global dedup API, asynchronous, HMAC-protected. Global query eligibility: first chunk of every file, plus any chunk whose last 8 hash bytes as LE u64 ≡ 0 mod 1024 → roughly one query per 4 MB. Server answers with a shard whose chunk hashes are HMAC-encrypted under a key in the shard header; the client proves possession by HMAC'ing its own chunk hash — raw hashes never leave the server, and a hit reveals only that chunk's xorb and position. Suggested minimum contiguous run 8 chunks, average run ≥ 1 MB (short runs fragment reconstruction). Max shard 64 MB. [Xet dedup spec](https://github.com/huggingface/hub-docs/blob/main/docs/xet/deduplication.md)
* **Upload protocol**: chunk → dedup → form ~64 MiB xorbs → `POST /v1/xorbs/default/{xorb_hash}` → build shard (file→terms map, verification hashes, optional SHA-256 for the git-LFS pointer) → `POST /v1/shards` (or streaming `POST /v2/shards`, NDJSON progress, fall back on 404). Global query: `GET /v1/chunks/default-merkledb/{chunk_hash}` → 200/404. All xorbs referenced by a shard MUST be uploaded first; uploads are idempotent (content-addressed). Concurrency is adaptive in xet-core (starts conservative, scales with bandwidth). Reconstruction = list of terms `(xorb_hash, [start,end))`, concatenated in order. [Xet upload protocol](https://github.com/huggingface/hub-docs/blob/main/docs/xet/upload-protocol.md)
* **Reported outcomes**: "faster uploads and downloads… by a factor of 2–3× in some cases" and the rationale that a pure chunk-level store creates too many CAS entries (hence xorbs) [From Chunks to Blocks](https://huggingface.co/blog/from-chunks-to-blocks); "~25 % dedupe across the Llama 4 family" (xet-team community post) **(extract)** [post mirror](https://huggingface.co/andrewrreed/activity/posts); a one-day snapshot of 8.2 M upload requests / 130.8 TB motivating a CAS-first design [Rearchitecting uploads](https://huggingface.co/blog/rearchitecting-uploads-and-downloads); Parquet writers now emit content-defined row-group boundaries so small table edits re-upload only changed chunks (HF hosts ~4 PB Parquet of ~21 PB) [Parquet CDC](https://huggingface.co/blog/parquet-cdc). Hub limits that shape layout: ≤ 10 k entries per folder, ≤ 100 k files per repo, 50 GB hard / 20 GB recommended per file. [HF storage limits](https://huggingface.co/docs/hub/en/storage-limits)

### 1.3 Dedup ratios actually reported

* **Whole-file vs block-level** (857 Microsoft desktops, FAST'11 best paper): whole-file dedup "achieves about three quarters of the space savings of the most aggressive block-level deduplication for storage of live file systems, and 87 % of the savings for backup images." This is the single most relevant number for the "whole-file only" decision: whole-file BLAKE3 identity already captures most of the win on general file trees; the remaining ~25 % is concentrated in large, iteratively edited files. [Meyer & Bolosky, FAST'11](https://www.usenix.org/conference/fast11/study-practical-deduplication)
* **LLM checkpoints / fine-tunes** (ZipLLM, NSDI'26): 54.1 % storage reduction across 3,048 sampled Hugging Face LLMs, ~20 % better than SOTA dedup+compression, via tensor-level dedup plus "BitX" lossless XOR-delta between a fine-tune and its base; storage is "overwhelmingly dominated by fine-tuned LLMs" with sparse parameter differences. [ZipLLM arXiv](https://arxiv.org/html/2505.06252v3), [NSDI'26 page](https://www.usenix.org/conference/nsdi26/presentation/wang-zirui)
* **Large storage studies** cited in CDC literature: up to 83 % space savings (Microsoft/EMC backup workloads) — an upper bound for backup, not for game assets. [SeqCDC (Middleware'24)](https://cs.uwaterloo.ca/~alkiswan/papers/SeqCDC_Middleware24.pdf)
* **Game assets (PSD/FBX/uasset)**: no published measured dedup ratio was found. Vendor statements only: Epic's Lore (open-sourced June 2026, MIT, Rust) uses content-addressed "reusable, indexed chunks", Merkle-tree revisions, sparse workspaces with on-demand hydration; no benchmarks, no chunker parameters published, locking still on the roadmap, pre-1.0 formats. [EpicGames/lore](https://github.com/EpicGames/lore) Anchorpoint and others claim "native chunking and deduplication" without numbers. [Anchorpoint comparison](https://www.anchorpoint.app/blog/best-source-control-software-for-unreal-engine) A patent describes uploading only missing chunks of game content to object storage to save WAN bandwidth, again without ratios. [USPTO 12685930](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12685930) **Gap: a benchmark on a real studio depot is required before promising a number.**

### 1.4 Verification: BLAKE3 tree hashing, Bao verified streaming

* BLAKE3 is "a Merkle tree on the inside": input split into 1024-byte chunks, 64-byte blocks, 32-byte chaining values, parallel across SIMD lanes/threads; default 256-bit output; not length-extendable; `rayon` multithreading in the Rust crate; Bao implements verified streaming on top of it. [BLAKE3 README](https://github.com/BLAKE3-team/BLAKE3) Reported throughput (secondary): paper cites ~12× SHA-256 single-threaded on Cascade Lake-SP; a 1 GB single-thread AVX-512 run at 10.5 GB/s; small inputs (< 1 KiB) get no tree parallelism and hardware SHA-256 can match it there. **(extract)** [lukechampine/blake3](https://github.com/lukechampine/blake3), [blake3 vs sha256 benchmark](https://shattered.io/blake3-vs-sha256-2026/)
* **Bao** encodes the BLAKE3 tree so any byte range can be verified against the *whole-file* hash while streaming: combined encoding = 8-byte LE length + chunks and 64-byte parent nodes in pre-order (no seeking); **outboard** encoding = parents only, data read from the original file; **slices** carry only the nodes needed for a range (chunks always inline). The decoder must not disclose length (EOF, seek-to-end) until the final chunk verifies; encodings are malleable (trailing bytes) but decoded bytes always equal the original. Overhead with 1 KiB groups ≈ 64 B per 1 KiB ≈ 6.25 % (derived from the structure); the `abao` fork uses 16 KiB chunk groups by default (1 KiB–1024 KiB selectable) → ~0.4 % outboard overhead; `bao-tree` validates each chunk against the outboard before serving. Bao is "beta cryptography software… not formally audited". [Bao spec](https://github.com/oconnor663/bao/blob/master/docs/spec.md), [abao](https://github.com/LumeWeb/abao), [bao-tree](https://docs.rs/bao-tree), [bao crate](https://docs.rs/crate/bao/latest)
* Design implication for Synergos: because the file identity is already BLAKE3, an outboard Bao tree (stored next to the blob, ~0.4 % at 16 KiB groups) gives verified HTTP-range/QUIC-stream resume and multi-source fetch **without** inventing a second chunk-hash scheme. CDC (for dedup) and Bao (for verification) are orthogonal and can coexist: CDC chunk boundaries define storage/dedup units; Bao defines verification units.

LAN rule of thumb from these numbers: lz4 decompresses at ~4–5 GB/s/core, i.e. above 10 GbE line rate, so it never becomes the bottleneck on LAN; zstd -1 compresses at ~0.5 GB/s/core, so a 1 Gbps WAN link is CPU-cheap but a 10 Gbps intra-studio sync needs either lz4 or ≥ 4 compression threads.

### 3.2 Dictionaries and long-range mode

* `zstd --train` builds dictionaries from many small samples ("a lot of small files (> 100)"); gains are "mostly effective in the first few KB"; one dictionary per data type. [zstd man page](https://man.netbsd.org/1/zstd.1), [zstd README dictionary section](https://github.com/facebook/zstd/blob/dev/README.md)
* `--patch-from=OLD` = dictionary compression where the dictionary is the previous version (windowSize > srcSize); cannot combine with `-D`. This is the cheapest way to get *delta-like* storage for versions of one asset without a differ: server keeps version N, stores N+1 as `zstd --patch-from=N`. [zstd man page](https://man.netbsd.org/1/zstd.1)
* `--long[=windowLog]` long-distance matcher, default windowLog 27 = 128 MiB window; windowLog > 27 requires the decoder to be told (`--long=31` / `--memory=2GB`); introduced in v1.3.2 which raised max window to 2 GB; on a concatenation of six Linux kernel tarballs only the 2 GB window matched across versions; multithreaded memory = window × threads. [zstd v1.3.2 release](https://github.com/facebook/zstd/releases/tag/v1.3.2)

### 3.3 What not to compress; detection

* Borg's `auto,C[,L]` mode tries lz4 on each chunk and stores "none" if it does not shrink; the first writer of a chunk fixes its compression. [borg-compression(1)](https://man.archlinux.org/man/borg-compression.1.en) Xet does the same per 64 KiB chunk (store uncompressed if LZ4/BG4 do not help). [Xet xorb spec](https://github.com/huggingface/hub-docs/blob/main/docs/xet/xorb.md) Steam always LZMA-compresses chunks before encryption. [SteamDB](https://steamdb.info/blog/steam-download-system)
* Recommendation: per-chunk trial compression (lz4 first, zstd only if lz4 gained > ~5 %) is the proven pattern; it makes PNG/JPEG/MP4/zip-wrapped FBX/.pak fall through to "none" automatically, without a format whitelist.

### 3.4 Texture formats and transcoding

* GPU formats are fixed-rate: DXT1/BC1 4 bpp (RGB), DXT5/BC7 8 bpp (RGBA), BC6H 8 bpp (HDR), BC4 4 bpp (single channel), ASTC from 8 bpp (4×4) to 0.89 bpp (12×12). [Unity texture compression formats](https://docs.unity3d.com/2022.2/Documentation/Manual/texture-compression-formats.html), [Unity format reference](https://docs.unity.com/en-us/engine/6000.7/manual/materials-and-shaders/textures/textures-getting-started/texture-compression-formats/texture-formats-reference)
* Basis Universal / KTX2: "compress once, transcode at load"; UASTC (BC7-class quality, fast transcode to BC7 and ASTC since it is a common subset) vs ETC1S (very small); optional RDO pass makes UASTC more LZ-compressible. [basis_universal README](https://skia.googlesource.com/external/github.com/BinomialLLC/basis_universal/+/refs/tags/v2_0)
* Unreal Cloud DDC stores derived (cooked/compressed) data as "compact binary objects in a content-addressable store that can be replicated across the world"; Virtual Assets pull bulk payloads from Perforce or a DDC backend on demand. [Unreal Cloud DDC setup](https://dev.epicgames.com/documentation/en-us/unreal-engine/how-to-set-up-a-cloud-type-derived-data-cache-for-unreal-engine), [Virtual Assets overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-virtual-assets-in-unreal-engine)
* Implication: version the **source** (PSD/TGA/EXR/PNG) once; treat BCn/ASTC/DDS/KTX2 as derived data keyed by (source hash, encoder settings), produced by a build service and cached like a DDC, never committed. This removes the largest class of "already-compressed, never-dedups" bytes from the VCS.

## 4. Transport

### 4.1 QUIC tuning (quinn specifics)

quinn `TransportConfig` defaults (read from source): congestion controller **Cubic** (`CubicConfig::default()`); `initial_mtu` = `min_mtu` = 1200; MTU discovery **on** (`MtuDiscoveryConfig`: `upper_bound` 1452, `interval` 600 s, `black_hole_cooldown` 60 s, `minimum_change` 20); `stream_receive_window` 1,250,000 B; `receive_window` VarInt::MAX; `send_window` 10,000,000 B; `max_concurrent_bidi/uni_streams` 100; `max_idle_timeout` 30 s; `initial_rtt` 333 ms; `packet_threshold` 3; `time_threshold` 1.125 RTT; `persistent_congestion_threshold` 3; `enable_segmentation_offload` true; `ack_frequency_config` None (if set: `ack_eliciting_threshold` 1, `reordering_threshold` 2, `max_ack_delay` None); `datagram_receive_buffer_size` 1,250,000; `datagram_send_buffer_size` 1 MiB; `max_outgoing_bytes_per_second` None; `keep_alive_interval` None. [quinn-proto transport.rs](https://github.com/quinn-rs/quinn/blob/main/quinn-proto/src/config/transport.rs)

* **Flow-control windows are the first bottleneck on high-BDP paths**: 1 Gbps × 100 ms RTT = 12.5 MB in flight, 10× the default per-stream window (1.25 MB). Raise `stream_receive_window` to ≥ BDP and `send_window` to ≥ (streams × BDP), or spread a blob across several streams. (Derived from the defaults above.)
* **Controllers**: `Cubic`, `NewReno`, `Bbr` (port of Google QUICHE BBR, draft-cardwell-iccrg-bbr; marked "Experimental! Use at your own risk"; `BbrConfig::initial_window` default 200 datagrams in code vs the documented recommendation `min(10·MDS, max(2·MDS, 14720))`). [congestion.rs](https://github.com/quinn-rs/quinn/blob/main/quinn-proto/src/congestion.rs), [bbr/mod.rs](https://github.com/quinn-rs/quinn/blob/main/quinn-proto/src/congestion/bbr/mod.rs) Field reports: moq switched quinn to BBRv1 for steadier send rate while other backends (noq, iroh) reverted from BBRv3 to CUBIC after an arithmetic-underflow panic in BBRv3 loss handling. [moq PR #2468](https://github.com/moq-dev/moq/pull/2468) Literature: QUIC-BBR flows take bandwidth from CUBIC over time, BBR favours higher-RTT flows, CUBIC won every mixed scenario in one testbed. [Fifty Shades of Congestion Control](https://arxiv.org/pdf/1903.03852) IETF BBR draft (v3) claims much higher throughput on shallow-buffer/lossy paths and lower queueing delay on deep buffers. [draft-ietf-ccwg-bbr-04](https://datatracker.ietf.org/doc/html/draft-ietf-ccwg-bbr-04)
* **GSO/GRO**: quinn-udp `BATCH_SIZE` = 32 (1 on Apple slow path); on Linux/Android GRO segments = 64 (`UDP_GRO_CNT_MAX`, receive buffer = max_udp_payload × 64); GSO is disabled (max_gso_segments → 1) on `EIO`/`EINVAL` from `sendmsg`, retrying once without `IP_TOS`; quinn removed `sendmmsg` as "not actually helpful in practice" when GSO is available. [quinn-udp unix.rs](https://github.com/quinn-rs/quinn/blob/main/quinn-udp/src/unix.rs), [quinn-udp lib.rs](https://github.com/quinn-rs/quinn/blob/main/quinn-udp/src/lib.rs), [quinn issue #1749](https://github.com/quinn-rs/quinn/issues/1749) Measured effect (quicly, Fastly): per-core throughput 240 → 348 Mbps coalescing 10 packets with GSO, 431 Mbps at 20; caveat that GSO bursts stress network buffers. **(extract)** [Fastly: QUIC vs TCP computational efficiency](https://www.fastly.com/blog/measuring-quic-vs-tcp-computational-efficiency) Firefox/neqo: GSO/GRO beat sendmmsg; Android limits GSO to ~10 datagrams; a single long-lived 64 KB receive buffer cut CPU on large transfers. [Inden, TUM 2025 talk](https://www.ce.cit.tum.de/fileadmin/w00cgn/cm/mir-2025/talks/2025-inden-talk-fast-udp.pdf) Cloudflare's 2019 quiche/NGINX work: sendmmsg, UDP GSO, pacing instead of as-fast-as-possible. [Cloudflare: accelerating UDP for QUIC](https://plushcap.com/analysis/cloudflare/accelerating-udp-packet-transmission-for-quic)
* **ACK frequency**: `ACK_FREQUENCY` frame (seq, ack-eliciting threshold, requested max_ack_delay in µs, reordering threshold) + `IMMEDIATE_ACK` + `min_ack_delay` transport parameter; motivation is CPU cost of ACK-only datagrams at high packet rates and asymmetric links. Status: draft-14 (Feb 2026), WG consensus, expired on the datatracker — not an RFC. [draft-ietf-quic-ack-frequency](https://github.com/quicwg/ack-frequency/blob/main/draft-ietf-quic-ack-frequency.md), [datatracker](https://datatracker.ietf.org/doc/draft-ietf-quic-ack-frequency/)
* **QUIC vs TCP on fast paths**: Chrome's QUIC "begins to fall behind when the bandwidth exceeds ~500 Mbps" and is 45.2 % slower than HTTP/2 at 1 Gbps; cause is receiver-side user-space packet/ACK processing; proposed fixes: UDP GRO, QUIC-aware offloads, multi-threaded downloads. [Zhang et al., WWW'24 (arXiv 2310.09423)](https://arxiv.org/pdf/2310.09423) ETH Zurich benchmark suite: kernel TCP reaches up to 3× the best QUIC stack; a quinn patch cut socket writes 4× (one syscall per GSO batch). [ETH thesis 2024](https://nsg.ee.ethz.ch/files/public/theses/2024-quic_benchmark_suite/thesis-1.pdf) Design consequence: for intra-datacenter 10 GbE bulk moves, a plain TCP/TLS or kernel-offloaded path can beat QUIC; QUIC earns its place on lossy/NATed WAN paths, multi-stream small-object fetch and migration.
* **0-RTT**: 0-RTT data is replayable; quinn's `Connecting::into_0rtt` docs: outgoing 0-RTT "should never trigger non-idempotent operations"; incoming 0.5-RTT data arrives before client authentication completes; `Connection::authenticated` resolves only once "proven not to be a replay attack"; server resumption state may be lost across restarts. [quinn connection.rs](https://github.com/quinn-rs/quinn/blob/main/quinn/src/connection.rs) RFC 9001 §9.2 / QUIC applicability: 0-RTT must not carry a self-contained trigger for any non-idempotent action; servers that accept it must keep a single-use/time-bounded replay cache keyed by PSK identity. **(extract)** [Trail of Bits on 0-RTT](https://blog.trailofbits.com/2019/03/25/what-application-developers-need-to-know-about-tls-early-data-0rtt/), [draft-ietf-quic-applicability](https://draft-ietf-idr-as4bytes.potaroo.net/ietf/ids/draft-ietf-quic-applicability-18.xml) For Synergos: content-hash GETs may ride 0-RTT (idempotent, but must still be rate-limited because replays amplify bandwidth); HMAC-signed PUTs, receipt issuance and any custody state change must wait for `authenticated`.
* **MTU**: start at 1200 (QUIC minimum), let DPLPMTUD probe to ~1452; disable probing where ICMP is filtered (OPNsense cloudflared note) and expect 1200-byte datagrams through tunnels/VPNs. [OPNsense cloudflared how-to](https://docs.opnsense.org/manual/how-tos/cloudflared.html), [MtuDiscoveryConfig defaults](https://github.com/quinn-rs/quinn/blob/main/quinn-proto/src/config/transport.rs)

### 4.2 Cloudflare Tunnel, CDN, WebTransport, multipath

* cloudflared connects to the edge on port 7844: UDP for QUIC, TCP for HTTP/2; UDP, ICMP and private-network (WARP) proxying **require** the QUIC transport; since 2022 cloudflared does not fall back to HTTP/2 when `quic` is explicitly selected; the move to QUIC was motivated by head-of-line blocking of HTTP/2 multiplexing; quic-go benefits from larger UDP socket buffers. [Cloudflare: tunnel with firewall](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/), [cloudflared CHANGES 2024.9.0](https://git.nixnet.services/curben/cloudflared-mirror/src/tag/2024.9.0/CHANGES.md), [cloudflared CHANGES 2023.2.1](https://git.nixnet.services/curben/cloudflared-mirror/blame/tag/2023.2.1/CHANGES.md), [Cloudflare blog: tunnels over QUIC](https://blog.cloudflare.com/getting-cloudflare-tunnels-to-connect-to-the-cloudflare-network-with-quic/), [TUN-7756 commit](https://git.nixnet.services/curben/cloudflared-mirror/commit/dcfc831752b88b30d7a4856438a09fd793b38437)
* No published per-tunnel bandwidth cap; Cloudflare says throughput is bounded by **ephemeral ports** (recommend 2 hosts × 4 cores/4 GB, 50,000 ports each; non-DNS UDP holds a port for the whole flow). [Cloudflare tunnel system requirements](https://developers.cloudflare.com/tunnel/platform/system-requirements/) Proxied HTTP request-body limit: 100 MB Free/Pro, 200 MB Business, 500 MB+ Enterprise; cacheable object limit 512 MB (Free/Pro/Business) and 5 GB default on Enterprise. [Cloudflare default cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior) ⇒ a custody PUT of a 2 GB blob through an orange-clouded hostname fails; blobs must go through chunked/multipart uploads under the body cap, a grey-cloud (DNS-only) origin, or the QUIC tunnel data plane, not the HTTP proxy.
* **WebTransport over HTTP/3**: draft-16, "In WG Last Call", intended Proposed Standard, last updated 2026-07-06; no RFC yet. [draft-ietf-webtrans-http3](https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/) **Multipath QUIC**: draft-21 (March 2026), in RFC Editor queue since 2026-05-20. [draft-ietf-quic-multipath](https://datatracker.ietf.org/doc/draft-ietf-quic-multipath) Neither is needed for v1; multipath is the eventual answer for Wi-Fi+LTE artist laptops.

### 4.3 Parallel multipart, resumable uploads, HTTP range

* **S3**: 10,000 parts per upload; part size 5 MiB–5 GiB, last part unbounded below; max object raised from 5 TB to **50 TB** on 2025-12-02 (all regions except GovCloud). [S3 multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html), [AWS What's New 2025-12](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-s3-maximum-object-size-50-tb/) Practical: with the 5 MiB minimum the cap is ~48.8 GiB, so part size must be ≥ ceil(size/10,000); GitLab hit exactly this (~50 GB) with default part sizes. [gitaly issue 6056](https://gitlab.com/gitlab-org/gitaly/-/issues/6056)
* **MinIO**: 10,000 parts; part 5 MiB–5 TiB (AIStor docs; older community docs say 5 GiB); single PUT ≤ 5 TiB; `mc put` example uses 20 MiB parts × 8 parallel. [MinIO thresholds (AIStor)](https://docs.min.io/aistor/reference/aistor-server/thresholds/), [MinIO thresholds (community)](https://docs.min.io/community/minio-object-store/operations/concepts/thresholds.html), [mc put](https://docs.min.io/minio/baremetal/reference/minio-mc/mc-put.html)
* **tus 1.0**: `HEAD` → `Upload-Offset`; `PATCH` with `Content-Type: application/offset+octet-stream` and matching `Upload-Offset` → `204`; mismatch → `409` (no change); `Tus-Resumable: 1.0.0` on every request; `Tus-Max-Size`; extensions: creation (`POST`→`201`+`Location`, `Upload-Defer-Length`), creation-with-upload, expiration (`Upload-Expires`), checksum (`Upload-Checksum`, SHA-1 mandatory, `460` on mismatch), termination (`DELETE`), concatenation (`Upload-Concat`) for **parallel partial uploads**. [tus protocol.md](https://github.com/tus/tus-resumable-upload-protocol/blob/main/protocol.md)
* **IETF successor** (`draft-ietf-httpbis-resumable-upload`, Standards Track, interop version 10, draft -13): `Upload-Complete`, `Upload-Offset`, `Upload-Length`, `Upload-Limit` (`max-size`, `min-size`, `max-append-size`, `min-append-size`, `max-age`), interim `104 Upload Resumption Supported` with `Location`, `PATCH` `application/partial-upload`, `409` returns the correct offset, `DELETE` cancels. Prefer this header set for Curare's upload API so browser/SDK clients converge. [draft-ietf-httpbis-resumable-upload](https://github.com/httpwg/http-extensions/blob/main/draft-ietf-httpbis-resumable-upload.md)
* **HTTP range**: RFC 9110 §14 (`Range: bytes=`, `206`, `416`, `If-Range` for safe resume against a changed representation, `Accept-Ranges`). [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-14) Content-addressed blobs make `If-Range` trivially safe (the ETag is the hash).

### 4.4 Peer-assisted distribution and relays

* **BitTorrent (BEP 3)**: piece length power of two, "most commonly 2^18 = 256 KiB" (older clients 1 MiB); SHA-1 per piece; 16 KiB request blocks ("all current implementations"); random piece order with **endgame** (request remaining blocks from everyone, cancel on arrival); choking: 4 unchoked by download rate, recomputed every 10 s, one optimistic unchoke rotating every 30 s, new peers 3× more likely. [BEP 3](https://github.com/bittorrent/bittorrent.org/blob/master/beps/bep_0003.rst) Rarest-first (ties broken randomly to keep piece distribution even) after a random-first phase of ~4 pieces; endgame must stay short because duplicates waste bandwidth. [libtorrent: fast piece picker](https://blog.libtorrent.org/2011/11/writing-a-fast-piece-picker/), [BitTorrent peer-selection analysis](https://arxiv.org/pdf/1402.2187)
* **Uber Kraken**: agent (registry API on every host) / origin (seeders on a self-healing hash ring over S3/GCS/HDFS) / tracker (orders peers into a pseudo-random regular graph) / build-index / proxy; ≥ 15 k hosts per cluster; > 50 % of max link speed per host; production > 1 M blobs/day incl. 100 k of ≥ 1 GB; peak 20 k blobs of 100 MB–1 GB in < 30 s; benchmark 3 GB image × 2,600 hosts at a 300 MB/s agent cap: p50 10 s, p99 18 s, p99.9 22 s; Uber caps blobs at 20 GB and recommends splitting > 10 GB. [Kraken README](https://github.com/uber/kraken/blob/master/README.md)
* **Dragonfly (CNCF graduated 2025-10-28)**: Manager / Scheduler (picks parents, decides back-to-source) / Seed Peer / Peer; `DefaultPieceSize` 4 MiB, `DefaultPieceSizeLimit` 15 MiB (`ComputePieceSize(length)`); peers download pieces from several parents in parallel; v2.5 peers can fetch pieces over `tcp` or `quic`. [Dragonfly docs](https://d7y.io/docs/v2.3.0/), [dragonfly internal/util](https://pkg.go.dev/d7y.io/dragonfly/v2/internal/util), [dfdaemon config](https://d7y.io/docs/next/reference/configuration/client/dfdaemon/), [CNCF v2.3.0 post](https://www.cncf.io/blog/2025/08/15/dragonfly-v2-3-0-has-been-released)
* **NAT traversal / relays (Tailscale)**: connections start over DERP and upgrade to direct UDP; direct success "well north of 90 % in typical conditions". [Tailscale NAT traversal improvements](https://tailscale.com/blog/nat-traversal-improvements-pt-1), [Tailscale peer relays](https://tailscale.com/blog/peer-relays-beta) Hard-NAT "birthday" probing: open 256 ports on the hard side, random probes from the easy side: ~50 % after 74 probes, 64 % after 256, 98 % after 1,024; 99.9 % needs ~170,000 probes (~28 min at 100 pps); both sides hard/random → relay. **(extract)** [How NAT traversal works (APNIC repost)](https://blog.apnic.net/2022/04/26/how-nat-traversal-works-nat-notes-for-nerds/), [Tailscale original](https://tailscale.com/blog/how-nat-traversal-works) DERP is a bandwidth sink (one trans-oceanic iperf anecdote: 2.2 Mbit/s); customer-run peer relays reach "throughput nearing that of a direct connection; often multiple orders of magnitude higher than" DERP. [simeononsecurity](https://simeononsecurity.com/articles/why-tailscale-uses-a-relay/), [Tailscale peer relays](https://tailscale.com/blog/peer-relays-beta) ⇒ Synergos should expect ~10 % of artist↔studio pairs to be relayed and must size the relay (Cloudflare tunnel or self-hosted) for full-rate traffic, or run studio-side "peer relays".
* **Erasure-coded multi-source fetch**: Storj uses Reed–Solomon k=29 of n=80 (expansion 80/29 ≈ 2.7×, > 11 nines durability); downloads request 39 pieces and cancel once the first 29 arrive — a hedged request that cuts tail latency; with replication instead of coding, tail latency is set by the hottest node. [Storj forum: RS numbers](https://forum.storj.io/t/future-changes-to-reed-solomon-numbers/9921), [Storj forum: replication](https://forum.storj.io/t/average-replication-on-storj/25074), [Taming tail latency (arXiv 1703.08337)](https://arxiv.org/pdf/1703.08337) For a 3–10 node history-node set the same effect is cheaper via Bao-verified **range striping**: ask each source for a disjoint byte range, re-issue slow ranges elsewhere (BitTorrent endgame), no coding overhead.

## 6. Decision matrix

Legend for "win": expected reduction of bytes moved or wall time per iteration, with the source basis; "cost": engineering/runtime cost. Numbers marked ≈ are derived from the cited parameters, not measured on these workloads.

| Workload | Biggest win | Why / evidence | Cost | Second-order wins |
|---|---|---|---|---|
| **PSD, 500 MB, iterative saves** (same artist saves 10–50×/day) | **CDC at 64 KiB (Xet parameters) + per-chunk trial LZ4 + xorb packing**; identity stays whole-file BLAKE3 | Whole-file dedup gives 0 % here (every save is a new hash); block-level is where the remaining ~25 % (Meyer–Bolosky) lives and it is concentrated in exactly this file class. A 500 MB file ≈ 8,000 chunks; one global-dedup query per ~4 MB ≈ 125 queries/save. Puffin-style canonicalisation is **not** needed for PSD layers unless "Maximize compatibility"/zip layers are on. No public PSD ratio exists — benchmark on studio data first. | Chunker ~1.5 GB/s/core + BLAKE3 → < 1 s CPU/save; index growth 8 k rows/version; xorb reconstruction (terms) adds a read-path. Must pin chunker constants + test vectors. | Fallback if CDC rejected: server-side `zstd --patch-from=prev` (no differ, 128 MiB–2 GB window) for storage only; transfer stays whole-file. |
| **FBX exports** (regenerated from DCC, binary FBX with deflate-compressed arrays) | **Store exports with compression off** (exporter setting) or Puffin-style deflate canonicalisation, then CDC | Deflate rewrites the whole stream on tiny mesh edits, so CDC on compressed FBX finds little; Chrome's Puffin exists precisely for this (huff ~10× faster than recompress). Uncompressed FBX + lz4 per chunk ≈ same wire size and chunk-stable. | Pipeline policy change (exporter preset); if canonicalisation is chosen, a deflate re-encoder must be deterministic across platforms. | Whole-file dedup catches unchanged re-exports (identical bytes) at zero cost. |
| **Texture sets** (PNG/TGA/EXR sources; BCn/ASTC/DDS outputs) | **Do not version derived GPU textures; build them as derived data (DDC-style, keyed by source hash + encoder settings) and serve via CDN/edge cache** | GPU formats are fixed-rate (4–8 bpp) and already incompressible; PNG is entropy-coded so CDC/zstd give ~0. Removing derived textures removes most "never-dedups" bytes; CDN object cap 512 MB/5 GB fits textures. | A build service + cache invalidation; Cloud-DDC-like replication. | Trial compression (lz4 probe) auto-skips PNG/JPEG. EXR/TGA sources do CDC-dedup across minor edits (uncompressed scanlines). |
| **Unity/Unreal project trees** (10^4–10^6 files, few huge) | **Lazy/sparse checkout with per-payload hydration (ProjFS/P4VFS-style on Windows, NFS-loopback elsewhere) + whole-file dedup + packed small-object fetch** | Whole-file dedup already yields ~75 % of block-level savings on general trees; the time cost is request count, not bytes → pack small blobs xorb-style and fetch over QUIC multi-stream (HoL-free); Unreal's Virtual Assets prove most editor tasks need only metadata. | VFS driver maintenance (Microsoft retreated to sparse-checkout); tools that walk trees defeat laziness; needs a per-payload API. | CDC for the few huge `.uasset`/`.umap`; exclusive locks (Perforce `+l` model) instead of deltas for unmergeable binaries. |
| **10 M-file image datasets** | **Shard into ~1 GB tars (WebDataset) + whole-file dedup of shards + P2P/cluster fan-out (Kraken/Dragonfly, 4 MiB pieces)** | Per-file requests dominate (HF caps 10 k files/folder, 100 k/repo); object stores want large sequential reads; Kraken moves 3 GB to 2,600 hosts with p99 18 s. CDC at 64 KiB is useless for < 8 KiB files (one chunk each). | Shard rebuild on edits (mitigate: append-only shards + tombstones; Parquet-CDC-style boundary alignment for tabular metadata). | lakeFS-mount-style lazy NFS for exploratory access; Bao-verified range reads inside shards. |
| **10–100 GB model checkpoints** | **CDC 64 KiB + ByteGrouping4-LZ4 + multipart/parallel upload (part ≥ 10 MiB) + Bao-verified multi-source download** | ~25 % dedup across a model family (Llama 4 on Xet); 54 % with tensor-aware dedup + XOR delta (ZipLLM); BG4-LZ4 is the only codec that helps bf16 tensors; 10,000-part limit forces ≥ 10 MiB parts for 100 GB; QUIC windows must be ≥ BDP (12.5 MB at 1 Gbps/100 ms). | Tensor-aware dedup needs safetensors parsing (format-specific); client memory for xorb assembly; GSO/GRO required to exceed ~500 Mbps per QUIC connection on one core, else use several connections or kernel TCP for DC-internal moves. | Cluster fan-out via seed-peer graph (Kraken > 50 % link rate on every host); 0-RTT only for hash GETs. |

### Cross-cutting recommendations for the Synergos/Curare redesign

1. Keep whole-file BLAKE3 as the identity and manifest unit (it already yields ~75 % of block-level savings and is what git pointers reference); add an **optional CDC chunk map** (Xet constants, published test vectors) for files above a size threshold (e.g. ≥ 8 MiB) — this reverses the 2026-08-16 "no CDC" decision only for the large-file tier where whole-file dedup is provably 0 %.
2. Add a **Bao outboard tree** per blob (≈ 0.4 % at 16 KiB groups) so every range read, resume and multi-source stripe is verified against the file hash — this is cheaper than Xet's separate term-verification hashes and reuses the existing BLAKE3 identity.
3. Treat compression as a per-chunk trial (lz4 probe → none/lz4/zstd/BG4) rather than a format whitelist.
4. Transport: QUIC for WAN/NAT/P2P with raised windows, GSO/GRO on, Cubic default, BBR behind a flag; kernel TCP allowed for LAN bulk; 0-RTT only for idempotent hash GETs; custody PUT/receipt only after `authenticated`.
5. Uploads: adopt the IETF resumable-upload header set (tus-compatible) with multipart parts ≥ max(10 MiB, size/10,000); never route > 100 MB bodies through the Cloudflare HTTP proxy.
6. Lazy workspaces: ProjFS on Windows, NFS-loopback on macOS, sparse checkout everywhere, with a per-payload fetch API so Unreal Virtual Assets / Unity importers can pull bulk data directly.
